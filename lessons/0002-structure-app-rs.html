项目结构与 src/app.rs

目标：看懂 app.rs 是怎么把路由、后台任务、命令行任务接到框架上的，并能从一条路由找到它的源文件。

1. app.rs 就是你以前手写的 main()

写 axum 时，你在 main() 里建 Router、挂 .route()、加 .layer()、最后 .with_state(state) 再 axum::serve。Loco 把这段装配代码拿走了，换成一个 trait：Hooks。你在 src/app.rs 里给 struct App 实现它，框架启动时回调这些方法——这就是 Rails 里“约定优于配置”的做法：你只说“有哪些东西”，框架负责“怎么接起来”。

生成的 src/bin/main.rs 只有一行实际代码：

cli::main::<App, Migrator>().await

它把你的 App 交给 Loco 的命令行，start、routes、db 等子命令都从这里进来。

路由在哪注册

你项目里 src/app.rs 的 routes（真实内容）：

fn routes(_ctx: &AppContext) -> AppRoutes {
    AppRoutes::with_default_routes() // controller routes below
        .add_route(controllers::auth::routes())
}
  • with_default_routes() 挂上第 1 课的 /_ping、/_health、/_readiness。
  • 每个 controller 文件导出一个 pub fn routes() -> Routes，在这里用 .add_route(...) 接进来。漏了这一行，handler 写得再对也是 404。

controller 那一侧（src/controllers/auth.rs 第 261 行起）：

pub fn routes() -> Routes {
    Routes::new()
        .prefix("/api/auth")
        .add("/register", post(register))
        .add("/login", post(login))
        .add("/current", get(current))
        // ……共 9 条
}

post(login)、get(current) 就是 axum 的 MethodRouter，一模一样。

和 axum 的对应：框架最后做了什么

Loco 1.2.0 源码 src/controller/app_routes.rs 的 to_router，去掉日志后就三步：

for router in self.collect() {
    app = app.route(&router.uri, router.method);   // 你熟悉的 Router::route
}
for mid in middlewares {
    app = mid.apply(app)?;                           // 你熟悉的 .layer()
}
let router = app.with_state(ctx);                    // 你熟悉的 with_state

这里的 ctx 就是 AppContext——Loco 替你定义好的 State 结构体（#[derive(Clone, FromRef)]，8 个字段：environment、db、queue_provider、config、mailer、storage、cache、shared_store）。所以 handler 里写：

async fn login(State(ctx): State<AppContext>, Json(params): Json<LoginParams>) -> Result<Response>

和你在 axum 里写 State(state): State<AppState> 是同一回事，只是结构体不用你自己定义。 出处：1.2.0 源码 src/app.rs；Coming from Axum

Hooks 里的其他方法

依据 1.2.0 源码。“必须”= 没有默认实现，不写编译不过。

方法必须？你项目里做了什么
app_name必须返回 crate 名
boot必须create_app::<Self, Migrator>(...)，带上数据库迁移
routes必须注册路由（上面讲的）
connect_workers必须注册后台任务 DownloadWorker（示例，perform 里是 TODO）
register_tasks必须注册 cargo loco task 能跑的任务：UserCreate、UserDelete
truncate / seed必须（仅有数据库时）清空 users 表 / 从 src/fixtures/users.yaml 灌数据
initializers可选生成的代码显式写了，返回空 vec![]
app_version可选拼 0.1.0 (dev)
middlewares、before_routes、after_routes、after_context、serve、on_shutdown 等可选没写，用默认。after_routes 可以直接返回一个现成的 axum Router

全表见 Hooks trait 参考。

2. 各目录放什么

Windows 上 loco new 默认 --os windows，会多一个 src\bin\tool.rs（见第 1 课）。完整的带注释结构图在 reference/project-structure.html。和后台 API 最相关的：

目录放什么
src/controllers/handler + 每个文件一个 routes()。应该保持薄：解析参数 → 调 model → 返回
src/models/_entities/Sea-ORM 根据表结构生成的实体，别手改
src/models/users.rs你的业务方法：find_by_email、create_with_password、verify_password……
src/views/注意：这个项目没有页面，这里放的是 JSON 响应结构体（LoginResponse、CurrentResponse），不是 HTML 模板
src/dtos/线上传输类型：现在只有 common.rs（分页 Page<T>、ApiError）。按官方教程，以后 scaffold 生成的请求/响应类型放这里
src/workers/后台任务（BackgroundWorker），请求里用 perform_later 丢进去
src/tasks/命令行一次性任务，cargo loco task <名字> 运行
src/mailers/邮件（注册欢迎信、找回密码）
src/initializers/启动时额外接线（现在是空的）
migration/src/建表/改表，每次变更一个文件
config/development / test / production 三套 YAML，端口、数据库、中间件开关都在这

DDD 视角（只点到）

官方立场：Loco 走 Rails 的 Active Record 路线——“胖 model、瘦 controller”，领域逻辑写在 model 上；明确说不要加 services/、repositories/ 目录，“model 就是领域对象，它自己知道怎么持久化”。 出处：Loco doctrine（官网发布，也随项目生成在 .claude/skills/loco/doctrine.md）

以下是我的建议，不是官方约定：粗略对应的话，controllers/ ≈ 接口层，models/<name>.rs ≈ 领域层（但和持久化绑在一起），models/_entities/ 和 migration/ ≈ 基础设施层，workers/、tasks/、mailers/ 介于应用层和基础设施之间。领域逻辑先按官方放进 models/<name>.rs；等后台管理的规则多到 model 装不下时，再讨论要不要拆出纯领域模块——那是和框架约定的取舍，后面单独讲。

注意第一个参数 auth: auth::JWT——它是个 extractor，请求没带合法 token 就进不了这个函数。这就是你学过的 axum extractor，第 3 课细讲。

文档和实际不一致处（以 1.2.0 实际为准）
  • Add a controller 里 cargo loco routes 的示例输出是扁平的 [GET] /_ping 列表；1.2.0 实际输出是上面那种树形。
  • Hooks 参考标的源码行号（src/app.rs:281-443）已过时，1.2.0 里 trait Hooks 在第 422 行起。另外那页说 impl Hooks for App 是 cargo loco generate 生成的，实际是 loco new 建项目时生成的。
  • 官方给编程助手看的 SKILL.md 说 views/ 放响应 DTO；但项目里同时还有 dtos/。现状是：auth 的响应在 views/，分页和错误类型在 dtos/。
