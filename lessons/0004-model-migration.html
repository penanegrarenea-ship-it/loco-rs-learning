model 和 migration

目标：用一条命令建出后台的 product 表（name:string! price:int status:string），弄清它生成了哪些文件、怎么注册的，然后在 admin controller 里加 GET /api/admin/products，从数据库读“在售商品”。

1. 先知道三件事

一个 model = 一个 migration + 一个生成的 entity + 一个你自己的 model 文件。migration 描述“表长什么样”；entity（src\models\_entities\products.rs）是 SeaORM 根据数据库里的真实表生成的 Rust 类型；src\models\products.rs 才是你写代码的地方。 出处：Add a model

_entities\ 每次都整个重写，别手改；models\products.rs 只生成一次。1.2.0 源码 src/db/entities.rs：db entities 调外部程序 sea-orm-cli 把所有表重新生成到 _entities\，再由 fix_entities() 检查 src/models/<表名>.rs：if !new_file.exists() 才创建，并往 models\mod.rs 追加 pub mod。所以你的代码放在 models\products.rs 里，以后改表、重新生成也不会丢。

业务规则写在 model 上，controller 只调用。Loco 是 Active Record 风格：官方 doctrine 主张“胖 model、瘦 controller”，不另建 services/、repositories/ 层。“什么算在售”这种规则就写成 impl Model 上的方法；保存前后的钩子写在 impl ActiveModelBehavior 里。 出处：Loco doctrine

2. 动手（在 playground\admin_api 真跑过）

PowerShell 写法，在 admin_api\ 根目录执行，先 Ctrl+C 停掉服务。我在 Linux 版 PowerShell 7 上跑，输出照实贴（日志行去掉了颜色和时间戳以外的噪音，路径显示为 /）。

③ migration 怎么注册的 
Select-String -Path migration\src\lib.rs -Pattern products
migration/src/lib.rs:6:mod m20261025_123659_products;
migration/src/lib.rs:14:            Box::new(m20261025_123659_products::Migration),

一处 mod，一处放进 Migrator::migrations() 的 vec!。app.rs 里的 Hooks 通过 migration::Migrator 拿到这个列表——没进 vec! 的 migration 永远不会跑。

迁移文件全文（ColType 是 Loco 的建表 DSL）：

async fn up(&self, m: &SchemaManager) -> Result<(), DbErr> {
    create_table(
        m,
        "products",
        &[
            ("id", ColType::PkAuto),
            ("name", ColType::String),
            ("price", ColType::BigIntegerNull),
            ("status", ColType::StringNull),
        ],
        &[],
    )
    .await
}

async fn down(&self, m: &SchemaManager) -> Result<(), DbErr> {
    drop_table(m, "products").await
}
你写的ColTypeRust 字段
name:string!String（NOT NULL）String
price:intBigIntegerNullOption<i64>
status:stringStringNullOption<String>
（自动）create_table 自带created_at / updated_at

规则：不带后缀 = 可空（Option），! = 必填，^ = 唯一。int 从 1.0 起是 i64，不是 i32。名字 product 被变成复数表名 products，和上一课 controller 前缀一样是 Rails 习惯。 出处：Add a model §2；源码 loco-gen column.rs：ScalarType::Int | ScalarType::BigInt => "BigInteger"

④ 生成的两个 model 文件

src\models\_entities\products.rs（别改）：

//! `SeaORM` Entity, @generated by sea-orm-codegen 2.0
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, Serialize, Deserialize)]
#[sea_orm(table_name = "products")]
pub struct Model {
    pub created_at: DateTimeWithTimeZone,
    pub updated_at: DateTimeWithTimeZone,
    #[sea_orm(primary_key)]
    pub id: i64,
    pub name: String,
    pub price: Option<i64>,
    pub status: Option<String>,
}

注意它带 Serialize，所以下面能直接 format::json(items)。src\models\products.rs（你的地方），生成时就有一个 ActiveModelBehavior：更新时自动刷新 updated_at，外加三个空的 impl Model {}（读）、impl ActiveModel {}（写）、impl Entity {}（查询器）。

命令做什么
db migrate执行所有 Pending 的 up
db status列出每个 migration 是 Applied 还是 Pending
db down执行最近 1 个的 down（db down 2 回滚 2 个；帮助：[STEPS] … [default: 1]）
db entities按当前数据库重写 _entities\（需 sea-orm-cli）
db reset删掉所有表，再重跑全部 migration；数据清空，不 seed
db truncate调 app.rs 的 Hooks::truncate，只清你在里面列出的表，不删表

没有 db up / db fresh（实测 error: unrecognized subcommand 'up'），往前走就是 db migrate。

down 会删表，表里的数据一起没了。以后手写 generate migration 改表时，顺序是 db migrate 再 db entities——entity 是从数据库读出来的，顺序反了就生成旧结构。

生成器不会帮你接 seed，要在 src\app.rs 的 Hooks 里各加一行（import 改成 models::_entities::{products, users}）：

async fn truncate(ctx: &AppContext) -> Result<()> {
    truncate_table(&ctx.db, users::Entity).await?;
    truncate_table(&ctx.db, products::Entity).await?;   // 新增
    Ok(())
}
async fn seed(ctx: &AppContext, base: &Path) -> Result<()> {
    db::seed::<users::ActiveModel>(&ctx.db, &base.join("users.yaml").display().to_string())
        .await?;
    db::seed::<products::ActiveModel>(               // 新增
        &ctx.db,
        &base.join("products.yaml").display().to_string(),
    )
    .await?;
    Ok(())
}

⑦ 在 model 上写规则，controller 只调用

src\models\products.rs：把顶部 use sea_orm::entity::prelude::*; 换成 use loco_rs::prelude::*;（要用到 ModelResult、QueryFilter、QueryOrder），导出加上 self，然后填 impl Model：

pub use super::_entities::products::{self, ActiveModel, Entity, Model};
use loco_rs::prelude::*;

// implement your read-oriented logic here
impl Model {
    /// 后台“在售商品”列表：领域规则（什么算在售）写在 model 上，controller 只调用。
    pub async fn list_on_sale(db: &DatabaseConnection) -> ModelResult<Vec<Self>> {
        let items = Entity::find()
            .filter(products::Column::Status.eq("on_sale"))
            .order_by_asc(products::Column::Id)
            .all(db)
            .await?;
        Ok(items)
    }
}

src\controllers\admin.rs 加三处：

use crate::models::products;

/// GET /api/admin/products —— 从数据库读在售商品
#[debug_handler]
pub async fn products(State(ctx): State<AppContext>) -> Result<Response> {
    let items = products::Model::list_on_sale(&ctx.db).await?;
    format::json(items)
}

// routes() 里：
        .add("products", get(products))

和 axum 比：ctx.db 就是你在 axum 里自己塞进 State 的连接池，Loco 在 AppContext 里替你建好了。ModelResult 的错误能被 ? 转成 Loco 的 Error，所以 handler 里直接 ?。

文档 / 提示和实际不一致处（以 1.2.0 实际为准）
  • generate model 成功后打印 “You can now apply it with cargo loco db migrate && cargo loco db entities”，但两步其实已经跑完（db status 显示 Applied）。Your First App 也写明 model/scaffold “already applied the migration”。这句提示是多余的。
  • Add a model 没提 db entities 依赖外部的 sea-orm-cli，也没提缺它时会停在一半；只有 Your First App 和 Add a database 页写了要装。
  • 文档没提生成器会对整个项目跑 cargo fmt，也没提会重写 _entities\users.rs 等已有 entity。（generate migration 也会跑 fmt：它把上面 app.rs 里我那行过长的 seed 调用拆成了多行。）
  • Seed data 说每行通过 A::from_json 转换；1.2.0 src/db/seed.rs 第 56–77 行实际是直接反序列化成 Model（注释说绕开 sea-orm 2.0 的问题），所以 NOT NULL 列（含 created_at）缺了就报 missing field。
  • db seed --reset 的帮助写 “Clears all data”，实际是 db::reset = 删表重建再跑全部 migration（src/boot.rs 第 366–369 行），不是 truncate。

3. 回忆题

你在 ① src\models\products.rs 里写了 list_on_sale。之后改表再跑 db entities，它和 ② src\models\_entities\products.rs 会怎样？

4. 练习

  1. 在你的 admin_api 里把 ⓪–⑧ 跑一遍（先 git commit 第 3 课的代码）。贴回：generate model 的 added:/injected: 几行、git status --short、Invoke-RestMethod 的表格。
  2. 给 products::Model 加 find_by_id(db, id: i64) -> ModelResult<Self>（找不到时返回 ModelError::EntityNotFound），再在 admin 里加 GET /api/admin/products/{id}。分别请求 /api/admin/products/1 和 /api/admin/products/99，贴两个状态码和响应体。
  3. 停服务，跑 cargo loco db down 和 cargo loco db status；再 cargo loco start，请求 /api/admin/products，贴状态码和响应体。表明明被删了，为什么不报错、而是返回这个结果？（提示：看启动日志的前几行和 config\development.yaml 的 database: 段。）最后用 cargo loco db seed --reset 恢复数据。
  4. 间隔复习（不看第 3 课）：生成器建 controller 时，把 admin 前缀变成了什么？今天生成 model 时，同样的习惯体现在哪里？
